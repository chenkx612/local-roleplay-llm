# Roleplay Post-Training 简历与面试参考

> 本文用于从当前仓库提炼简历项目经历和面试材料，不替代实验报告。
> 内容以 `morgana-v2` 的代码、冻结数据和收尾报告为依据；使用时应按岗位要求取舍，
> 不应把未执行的统一 Eval 或未通过的模型写成已完成成果。

## 1. 项目名与一句话定位

**项目名：** Roleplay Post-Training：小规模角色扮演模型后训练闭环

**一句话定位：** 围绕 `Qwen3.5-2B` 搭建角色扮演模型的轻量后训练实验系统，覆盖 Persona 建模、
数据构建、Base 评测、QLoRA SFT、DPO、GRPO、分层评测与实验复盘，并通过冻结输入、哈希清单、
原子写入和训练有效性门槛保证小样本实验可检查、可比较。

**适合强调的项目性质：**

- 学习型、研究型个人项目，而非生产训练平台。
- 重点不是训练出通用最优模型，而是用最小规模走通主要后训练方法链路，并形成可靠的实验结论。
- 最有价值的结果包括成功结果、失败定位和停止决策，而不只是最终模型分数。

## 2. 项目概述

项目以单个角色“摩尔加纳”和 2B 参数模型为实验对象，将角色设定转化为可训练、可评测的数据与
规则，完成以下链路：

```text
Persona / 风格样例
        ↓
Prompt 生成、去重与固定种子切分
        ↓
Base 推理基线
        ↓
Teacher-corrected SFT 数据 → FP32 QLoRA SFT
        ↓
主观偏好 DPO / 主观 Judge GRPO 探索
        ↓
本地连续规则奖励 GRPO
        ↓
post-GRPO DPO 定向修复
        ↓
自动稳定性检查 + 匿名人工 A/B + 分阶段复盘
```

代码侧提供统一 `roleplay` CLI，数据、训练、推理和评测均有明确入口；实验侧冻结模型 revision、
数据哈希、随机种子、训练配置和运行产物，避免因为数据漂移、后端不一致或失败写盘而得到错误结论。

## 4. 核心工作与可证明成果

### 4.1 数据与 Persona 工程

- 将角色身份、性格、语言风格、关系、边界和事实约束结构化为 Persona，并渲染为 system prompt。
- 从日常对话、背景与关系、情绪与选择、语言风格、出戏与冲突五类场景构建 100 条 Prompt，
  使用固定 seed 切分为 SFT 50、偏好/RL 20、Dev 10、Eval 20。
- 对规范化精确重复、跨 split 重复、长文本高相似重复、说话视角反转和目标元数据泄漏做校验；
  v2 的 100 条 Prompt 全局唯一，且与 v1 的 105 条历史 Prompt 无精确或高相似重复。
- 采用“全部文件暂存成功后再发布”的整批原子写入；API 重试或生成数量不足时不覆盖已有正式数据。
- 构建 50 条 Teacher-corrected SFT 标签，并根据 Dev bad case 增加 12 条定向样本，最终形成
  62 条 SFT 数据；定向覆盖主客体识别、事件与情绪、身份边界、问题意图和回答相关性。
- 为 post-GRPO DPO 另外构建 90 条训练 Prompt、9 条隔离 holdout 和 61 对偏好数据，覆盖背景编造、
  视角错位和情绪承接三类问题，并审计 Teacher chosen 比例和修改合同。

### 4.2 训练链路与有效性验收

- 使用 ms-swift 和 bitsandbytes 实现 4-bit NF4 QLoRA，覆盖 SFT、DPO、主观 Judge GRPO、
  规则型 GRPO 和 post-GRPO DPO。
- 识别出一次“训练命令成功但实际无效”的 FP16 隐式配置问题：前 6 个 `grad_norm` 为 `NaN`；
  该 run 被标记为 `training_failed`，没有发布 adapter 或继续行为评测。
- 将训练有效性从“退出码 + checkpoint”升级为硬门槛：检查实际生效的 FP16/BF16/dtype、
  optimizer step 数、所有梯度有限且为正、LoRA-B 非零更新、adapter 张量有限以及重载生成。
- 最终 SFT 使用 62 条数据训练 3 epochs，共完成 48/48 optimizer steps；三个 epoch 平均 loss
  从 `2.7107` 降至 `2.2956`、`2.1124`，186/186 个 LoRA-B 张量产生非零更新。
- 为各阶段实现独立 run 目录、环境与 Git 上下文记录、输入/输出哈希、失败摘要、release bundle
  与安全解包；拒绝覆盖既有 run、哈希篡改和压缩包额外路径。

### 4.3 评测体系

- 将质量门槛分为三层：先判断生成稳定性，再评估角色一致性，最后评估对话质量。
- 自动检查覆盖空回答、截断、乱码、严重复读、括号异常、错误自称、输出数量和 ID 对齐；
  动作格式、emoji 和长度等只作为诊断项，不让低价值格式指标单独否决整体改善。
- 使用固定 seed 和同一推理后端生成 Base/候选模型对照，并生成匿名、顺序可复现的人工 A/B 包；
  answer key 与评审包分离，降低位置偏差和先验偏差。
- SFT 相对同后端 Base 的 10 条 Dev 人工复核结果为胜 10/10、明显落后 0/10、无阻断性严重问题。
  生成稳定性、角色一致性、对话质量均分分别从 `3.3/1.4/1.5` 提升到 `8.0/5.2/5.7`。
- 当前代码有 18 个测试文件、299 个离线测试，覆盖数据去重与回滚、API 重试、冻结输入、
  训练参数漂移、梯度与 adapter 检查、奖励函数、匿名评测和 release 安全；
  2026-08-15 使用 `.venv/bin/python -m unittest discover -s tests -v` 验证全部通过。

### 4.4 奖励建模与受控实验

- 首轮 GRPO 使用在线主观 Judge，对 4 个候选进行组内排序；虽然技术训练通过，但人工结果仅胜
  2/10，三项质量均分全面低于 SFT，因此停止该路线。
- 将 GRPO 目标收窄为可自动验证的规则下限，设计本地 Reward v2：用连续违规距离度量长度、句数、
  动作、自称和格式，并对不可读、截断、乱码、严重复读等设置硬门控。
- Reward v2 消除了训练组奖励大量并列和零方差问题；最终规则型 GRPO 的 20 个训练组均有可区分
  奖励，平均组内标准差为 `1.632`，零方差组为 0。
- 在 10 条 Dev 上，规则型 GRPO 将规则均分从 `-3.123` 提升到 `-0.949`，增量 `+2.174`，
  规则分胜 7/10，硬无效与生成退化从 2 条降为 0。
- 人工抽查仍发现背景编造、视角错位和情绪承接问题，因此只将该 run 定义为“规则指标改善”，
  没有把奖励提升包装成整体角色质量提升。

### 4.5 实验判断与停止条件

- 多轮前置 DPO 使用 17～31 对偏好数据，尝试绝对质量门、最小分差、RPO 和最小编辑 pair，
  均未稳定超过 SFT；实验表明正 preference margin 可能来自进一步压低 rejected，而不是提升 chosen。
- 六次 post-GRPO DPO 在 20 或 61 对数据上进行学习率/RPO 受控比较。最佳 Reward v2 run 仍出现
  错误自称和生成稳定性回退，因此全部标记为 `automatic_review_failed`。
- 达到预设停止条件后停止继续扫描学习率、RPO、batch size 和 epoch，保留负向结果，并将下一轮
  优先级转向扩大独立 holdout、提高语义覆盖和修复 chosen 隐藏缺陷。

## 7. 面试叙事素材

### 7.1 案例一：训练跑完为什么不代表训练有效

**背景：** 一次 SFT 正常退出并生成 checkpoint，但模型行为没有可信改善。

**分析：** 检查训练日志发现前 6 个 `grad_norm` 为 `NaN`，进一步检查发现 ms-swift 在未显式配置时
启用了 FP16。仅看 loss、退出码和 checkpoint 会把无效训练当成成功。

**行动：** 显式关闭 FP16/BF16，将模型计算、BNB compute 和 LoRA dtype 固定为 FP32；在训练工作流
中增加实际参数、有限梯度、step 数、LoRA-B 非零更新和 adapter 重载检查。

**结果：** 失败 run 被阻断在行为评测前；最终 SFT 完成 48/48 steps，186/186 个 LoRA-B 张量更新，
并通过自动与人工门槛。

**面试重点：** 体现训练诊断能力、对框架隐式默认值的警惕，以及“技术门槛先于模型评分”的实验意识。

### 7.2 案例二：奖励上涨但模型未必更好

**背景：** 主观 Judge GRPO 没有稳定改善质量，而规则奖励早期又存在大量并列和零方差组。

**分析：** 主观目标难以由小样本在线 Judge 稳定表示；离散规则只给出是否违规，不能形成足够的
组内排序信号。

**行动：** 将目标缩窄为生成稳定性、长度、句数、动作、自称和格式等可验证下限，使用连续违规距离
构造 Reward v2，并保留人工角色一致性与对话质量评测作为独立门槛。

**结果：** 零方差组降为 0，规则 Dev 均分提升 2.174；但人工抽查仍发现背景和视角问题，因此没有
把规则分提升当成整体模型提升。

**面试重点：** 可讨论 reward hacking、proxy metric、奖励可学习性，以及自动指标与人工评测分工。

### 7.3 案例三：如何避免小数据实验得出假结论

**背景：** 项目只有单角色和百级样本，任何重复、泄漏、后端变化或少数异常样本都会明显影响结论。

**行动：** 固定模型 revision、seed、聊天模板和生成参数；在 split 前进行全局去重；使用同后端对齐
Base 与候选输出；冻结 Dev/holdout/Eval；为输入和产物保存哈希；匿名 A/B 时分离 packet 与 answer key。

**结果：** 数据漂移和残缺写盘可以被自动拒绝，阶段间比较有明确边界；同时能诚实识别 9 条 holdout
均值过于脆弱，不用单个最高分 run 代替整体结论。

**面试重点：** 体现数据治理、实验设计、可复现性和结论边界意识。

### 7.4 案例四：失败的 DPO 实验产生了什么价值

**背景：** 多轮 DPO 使用更严格的数据质量门、RPO 和最小编辑 pair，仍未稳定超过 SFT。

**发现：** preference margin 的改善经常主要来自 rejected 概率下降，chosen 的绝对似然仍下降；
17～61 对数据也不足以稳定覆盖复杂角色语义。

**决策：** 不将失败 adapter 继续传给 GRPO；规则型 GRPO 从已验证 SFT 重新开始。六次 post-GRPO
DPO 都触发自动回退门槛后停止超参扫描，将下一步改为扩充独立评测和改善数据语义覆盖。

**面试重点：** 强调负向实验、单变量归因、停止条件和避免 sunk cost，而不是只罗列训练算法。

## 8. 常见追问与回答要点

### 为什么选择 2B 模型和小数据？

项目目标是学习完整后训练流程，而不是追求榜单效果。2B 模型、单卡 QLoRA 和百级数据使每个阶段
都能在短反馈周期内产生可检查产物；通过缩小各阶段规模而不是删除 SFT、DPO、GRPO 或评测阶段，
保留了完整方法链路。

### 为什么主要使用 FP32，而不是更快的 FP16/BF16？

在实际环境中，隐式 FP16 已产生 NaN 梯度和零 LoRA-B 更新。项目优先保证学习实验有效、可诊断，
因此在 2B 小模型和单卡预算可接受的前提下固定 FP32。这个选择是针对当前硬件与框架组合的工程
决策，不代表 FP32 普遍优于 BF16。

### SFT 为什么改善明显？

同后端 Base 本身退化较多，而 62 条训练数据又直接覆盖角色边界、主客体识别、情绪和相关性。
因此 SFT 的相对提升可信，但胜 10/10 也受到 Base 较弱和 Dev 只有 10 条的影响；结论只限于当前
角色、模型、Prompt 和采样条件。

### 为什么 DPO 没有成功？

可能因素包括偏好对数量少、chosen 仍有隐藏缺陷、目标同时包含多个复杂语义维度，以及 token 级
训练学习了偶然措辞而非可泛化偏好。当前证据只能说明这些具体设置没有稳定超过 SFT，不能外推为
DPO 对角色训练无效。

### 规则型 GRPO 的价值是什么？

它验证了连续、可排序的本地规则奖励能为小规模 GRPO 提供有效信号，并改善输出的客观下限；同时
也显示规则奖励无法覆盖事实可靠性、视角和自然度，所以应作为过滤器或回归门，而不是整体质量总分。

### 如果继续做 v3，优先改什么？

先定义唯一主目标并冻结更大的语义 holdout；把背景编造、视角错位、情绪承接和错误自称 bad case
转换为新的训练分布；逐条审计 chosen/rejected 的单一缺陷合同；最后在同一后端、revision、模板、
参数和 seed 下执行冻结 Eval，比较 Base、SFT 和所有晋升候选。
